# GuomanTracker 产品 Roadmap

## 重点

- **统一节目数据来源**：节目目录、补录与资料更新统一持久化到 PG，
  游客和登录用户均读取数据库目录，移除目录 JSON 读取与回退逻辑。
- **取消手动同步**：本轮移除刷新日历、同步日历等入口；
  页面加载和刷新只读取数据库，不由用户触发官网抓取。
- **按排期密集扫描**：只在官方更新时间附近密集核验更新，
  成功后写入 PG；不建设独立的周期兜底扫描。
- **人工确认更新**：自动扫描未成功时，用户可通过按钮打开对话框，
  提交对应新集的官方链接，程序核验真实更新并保存到 PG。
- **本期排行**：首位点击人工更新按钮且核验成功的用户优先上榜；
  与“第一时间看”按钮的结合规则后续讨论。以上扩展仍处于规划阶段。

## 一、本轮范围：统一存储与目录读取

状态：核心发布于 2026-10-16 完成。PG 数据迁移、公共目录 HTTP 读取、
个人函数和静态网页均已上线，正式域名游客当前读取 3,248 个节目成功。
真实账号补录已有节目、进度保存和刷新读取，以及正式筛选、周历、手机宽度验收已通过。
管理员依据官方资料更新 PG 后，正式浏览器刷新复读已通过。
腾讯元数据识别修复后，真实新节目补录、PG 保存与游客页面读取均通过，测试产生的个人状态已恢复。
优酷官网返回验证页或缺少可信标题时仍拒绝补录，
详见[发布记录第十节](../02.%20ARCHITECTURE/PG目录统一发布记录.md#十云端识别修复与新节目持久化验收2026-10-16)。

- 节目目录以 PG 为唯一数据来源，游客也读取 PG 公共目录。
  个人追番、进度和优先级继续要求登录，并按账号隔离。
- 补录和资料更新必须保存到 PG，不能只更新页面或服务内存。
  未取得持久化成功确认时，不提示保存成功。
- 去除目录 JSON 的读取、打包和回退逻辑。
- 移除刷新日历、同步日历等手动抓取入口。
  页面刷新仅重新读取数据库，不触发官网采集。
- 数据库不可用时，保留当前页面已经加载的内容并明确提示错误；
  首次加载失败则显示错误与重试入口，不使用内置 JSON 目录兜底。

## 二、核心扩展：按排期密集扫描、人工确认与本期排行

状态：规划于 2026-10-30 调整，尚未实现，未安排发布日期。
本节替代此前将常规周期扫描作为独立落地项的设想。

### 2.1 用户目标

按排期密集扫描解决的是：**如何第一时间将官方剧集更新消息传递到网站**。
程序在官方更新时间附近主动核验，成功后将新集资料保存到 PG，
让目录、周历与观看推荐读取同一份更新结果。

自动扫描可能因官网限流、解析失败或其他问题未能确认更新。
用户发现官方已经发布新集时，可以主动提交这一集的官方链接，
由程序核验并补充更新数据库。

追番用户会在动漫弹幕中发送“第一”“第一”等词语，表达自己是最先观看的一批人。
产品计划提供最新剧集的专属按钮与本期排行榜，承接这种参与感。

### 2.2 基于官方更新时间的密集扫描

1. 最开始抓取节目资料时，同时获取官方更新时间，例如每周六 11:00。
2. 在临近更新时间的前五分钟开始，有计划地扫描对应官方接口或网址。
   例如周六 11:00 更新，则从周六 10:55 开始；时间示例按北京时间理解。
3. 扫描采用固定间隔或小范围随机间隔，具体间隔暂未确定。
4. 官网确认更新后，将新剧集资料、核验结果与处理状态写入 PG，
   完成本期更新，停止针对该次更新的密集扫描。
   网站目录、周历与观看推荐读取同一份数据库资料。

排期时间已到不能直接视为剧集已发布，仍需校验官方实际更新结果。

**不建设独立的周期兜底扫描**，不按用户目标每 6 小时、
热门目标每 24 小时等常规周期再次检查。
定时调度仅用于启动官方更新时间附近的扫描窗口；
窗口内的重试规则、窗口结束条件及延期处理仍需设计。
本期扫描未成功时，由下述人工确认入口补充更新。
后续各期仍按各自的官方更新时间启动扫描。

按排期扫描仍需具备读取节目资料、核验并写入 PG 的能力；
这部分作为密集扫描功能的一部分实现，不单列旧扫描器的周期运行项目。

### 2.3 人工确认更新入口

1. 用户发现某部动漫已有新集，点击该动漫的人工更新按钮。
2. 页面弹出对话框，由用户填写对应更新集数的官方播放链接。
3. 程序检查官方链接格式，并通过官方页面或接口资料核验：
   链接属于当前动漫、对应明确集号的正片，而且已经实际发布。
4. 核验成功后，将确认的集数和相关资料持久化到 PG；
   只有数据库确认保存成功，才向用户显示更新成功。
5. 链接无效、节目不符、属于预告或无法确认已发布时，
   不更新已确认的集数；数据库保存失败时不提示更新成功。

正则可用于链接格式校验，以及从官方响应中提取节目或集数信息；
**仅链接匹配正则不能证明该集已经发布**，更新依据须来自可信官方资料。
具体采用哪些官方页面、接口及解析规则，留待实现设计。

人工入口是针对具体动漫、具体新集的证据提交与核验，
不恢复原来的全目录刷新日历或同步日历入口，
不因普通页面加载或刷新触发官网采集。
它只更新公共节目资料，不自动修改个人观看进度。

### 2.4 与“第一时间看”按钮及本期排行的关系

**首位点击人工更新按钮且核验成功的用户优先上榜**。
未能确认官方更新或未成功保存到 PG 时，不作为成功更新参与。
人工确认更新与“第一时间看”按钮存在关联，
但是否合并按钮、已被自动扫描确认的剧集如何参与，
以及后续用户如何上榜，均留待后续讨论。

原“第一时间看”按钮表达用户第一时间观看的参与意愿；
点击、提交链接或跳转官方播放均不自动等同于实际开始或完成观看。
“先点击且最终成功”的时间依据、同时提交的先后判定，
以及自动扫描和人工提交并发确认时的排名规则尚未确定。

### 2.5 点击次数与负载限制

此前对“第一时间看”按钮暂拟 **3 次**限制，以控制官方核验请求。
本次未确定人工更新入口是否沿用或共用该额度。
次数按用户、剧集还是时间周期计算、何时重置，
以及校验失败、重复提交等情况是否扣减，均留待设计。

### 2.6 后续需要设计的内容

- **扫描规则**：具体间隔、随机范围、窗口持续时间、窗口内重试、
  延期与缺失排期处理、平台限流与资源预算，以及扫描结果的 PG 保存。
  这些规则不引入扫描窗口之外的常规周期兜底。
- **人工核验**：按钮与对话框交互、支持的单集链接形式、
  官方资料的节目归属与已发布判定、重复提交的处理和失败提示。
- **更新一致性**：自动扫描与人工核验并发更新、集数不回退、
  已确认资料的复用，以及 PG 保存结果不确定时的处理。
- **排行规则**：人工更新与“第一时间看”按钮的结合方式、
  首位成功用户的判定、重复参与、用户身份要求，
  以及“本期”的平台、节目和剧集划分。
- **请求控制**：人工入口与原 3 次设想的关系、额度统计与扣减口径、
  并发核验的合并复用、排名写入的去重与一致性规则。

本次只调整产品规划，不新增扫描任务、用户按钮、排行榜或次数限制实现。
